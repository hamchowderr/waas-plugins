# AnyPress plugins: agent guide

WordPress plugins for AnyPress, one Composer package each under `packages/`:

| Package | Runs on | Notes |
|---|---|---|
| `anypress-host` | The storefront (a seller's WordPress shop, e.g. shop.anypress.io) | Sells stores on FluentCart (main route) or WooCommerce; talks to the provisioning API |
| `anypress-client` | Every customer store, via the store template | One-click login, plan roles, the site-editing API and its WordPress abilities |
| `anypress-payments` | The storefront | Authorize.Net card payments for FluentCart |
| `anypress-export` | Any WordPress site being moved to AnyPress | Exports the site to an import code |
| `anypress-move` | Any WordPress site | AnyPress Client's moving switches on their own (Tools, Move to Fluent); `scripts/build-move.sh` copies them into `lib/`, never edit there |
| `anypress-updater` | Shared | `scripts/sync-updater.sh` copies it into host and payments; never edit those copies |

How they fit together: `docs/architecture/`. Releases and the update channel: `docs/releases.md`.

## Building and testing

- In the package you change: `composer install`, then `composer test -- --exclude-group mock` (the `mock` group needs network). CI runs PHP 8.1 and 8.3, so keep code valid on 8.1.
- Code checks, in `tools/qa`: `composer install`, then `composer phpcs` (WordPress Coding Standards with PSR-12 layout, `phpcs.xml.dist`; `composer phpcbf` fixes layout) and `composer stan` (PHPStan level 5 and ShipMonk's dead code check, `phpstan.neon.dist`). CI fails on coding standards errors, any PHPStan finding not in `phpstan-baseline.neon`, and Plugin Check errors. Remove code the dead code check reports instead of adding it to the baseline; `tools/qa/WordPressUsageProvider.php` teaches it the uses it can't see (hooks, REST callbacks, WP-CLI commands, other plugins' parent classes).
- `scripts/playground`: `npm ci`, then `npm run smoke` (AnyPress Client's site-editing API and abilities on WordPress Playground with the AnyPress theme), `npm run export` (AnyPress Export end to end), `npm run forms` (AnyPress Client's forms switch from Contact Form 7, WPForms and Ninja Forms to Fluent Forms), `npm run shop-switch` (AnyPress Client's shop switch from WooCommerce to FluentCart, with HPOS off and on), `npm run crm-switch` (AnyPress Client's CRM switch: WooCommerce buyers, MailPoet and Newsletter subscribers into FluentCRM, with HPOS off and on), `npm run moving` (AnyPress Client's support, affiliate and community switches: Awesome Support, SliceWP and BuddyPress into Fluent Support, FluentAffiliate and FluentCommunity), `npm run courses` (AnyPress Client's course switch: LearnDash courses, students and progress into FluentCommunity courses, on a community store; `FLUENT_COMMUNITY=<version>` for another release), `npm run lms` (the same course switch from Tutor LMS and LifterLMS, both installed from wordpress.org, on a community store; `TUTOR=`, `LIFTERLMS=`, `FLUENT_COMMUNITY=<version>` for other releases), `npm run memberpress` (AnyPress Client's MemberPress switch on a community store: active members into FluentCommunity spaces and courses with FluentCRM tags, from seeded MemberPress tables), `npm run move` (AnyPress Move, the switches as their own plugin, on a plain WordPress: the Tools page's Check, Switch and Undo for a Tutor LMS course, and nothing when AnyPress Client is active; `scripts/build-move.sh` first), `npm run circle` (AnyPress Client's Circle switch on a community store: a Circle community into FluentCommunity through a fake Circle Admin API; `FLUENT_COMMUNITY=<version>` for another release), `npm run mail-log` (AnyPress Client on a community store: FluentCommunity's notification emails stay out of FluentSMTP's email log, other emails stay in it), `npm run community-portal` (AnyPress Client on a community store: FluentAuth's Login Redirects on FluentCommunity's own sign-in, Settings > Reading's community-on-the-home-page choice, members kept out of wp-admin), `npm run phone` (AnyPress Client's phone receptionist routes: FluentBooking times and bookings, callers into FluentCRM), `npm run highlevel` (AnyPress Client's HighLevel link: WP Fusion Lite connected to the site's HighLevel sub-account by itself, new users sent as contacts), `npm run admin-audit` (every wp-admin screen of a store built like the template, with `--client` and `SITE_TYPE=<site type>` for a store of that type with AnyPress Client's clean wp-admin: notices, pop-ups, upsells and menus written to a report with screenshots), `npm run domains` (AnyPress Host's domain checkout: search on the Website page, FluentCart checkout for a yearly domain, registration and renewal through a fake API), `npm run storage-packs` (AnyPress Host's storage packs: the Website page's "Add 25 GB storage" link and its FluentCart checkout, then buying, stacking, pausing, resuming and cancelling packs, each sending the store's pack count through a fake API), `npm run support` (AnyPress Host's support desk: the API's signed calls open, read, answer and close tickets in Fluent Support, and the Support page; `FLUENT_SUPPORT=<version>` for another release) `npm run languages` (AnyPress Client's Languages switch: Polylang set up on an online-store or `SITE_TYPE=community` site, a page's Spanish copy at `/es/`, the menu's language switcher), `npm run products` (AnyPress Client's shop product routes on an online-store site: products made by FluentCart's importer as drafts, with photos) and `npm run shop` (a copy of shop.anypress.io with its design from `scripts/test-storefront/remote/design`; `-- --shots` screenshots every page). Playground uses SQLite; plugins that need MySQL warn there but most still work.
- `scripts/test-env.sh` and `docker-compose.yml`: a full local storefront with the Host plugin.
- After changing `packages/anypress-updater`, run `scripts/sync-updater.sh`; CI fails when the copies drift.

## Releasing

Raise the version in the PR; merging it to `main` releases it (**Release on merge**, `release-on-merge.yml`, which runs **Tag and release plugin** for every plugin whose version has no tag yet, with the merge commit's message as the changelog). Run **Tag and release plugin** (`tag-release.yml`, GitHub `actions_run_trigger`) by hand only to release an older commit. Tags: `anypress-host-vX.Y.Z`, `anypress-client-vX.Y.Z`, `anypress-payments-vX.Y.Z`, `anypress-export-vX.Y.Z`; `-beta.N` goes to the beta channel only. Bump the plugin header and its version constant in the same PR as the change.

AnyPress Client never updates itself in stores: a new release reaches stores only through a new store template version built from `waas-provisioning-api/templates/anypress-store`.

## Building for WordPress

- Use the WordPress skills in `.claude/skills/` (list in its README): `wp-plugin-development` for structure and security, `wp-rest-api` for routes, `wp-abilities-api` and `wp-abilities-verify` for abilities, `wp-playground` and `blueprint` for tests and previews, `wp-phpstan` for static analysis.
- Stores run WordPress 7.1 on PHP 8.3 with the **AnyPress** block theme (`hamchowderr/anypress-theme`; stores made before it run Ollie). Anything AnyPress Client adds to a store's pages must be block markup that uses the theme's patterns and its `theme.json` colour, font and spacing slugs, not fixed values (`wp-block-themes`, `wp-patterns`). Store pages are edited in WordPress, never headless.
- Every Playground blueprint and preview installs the AnyPress theme from `scripts/playground/preview-zips/anypress.zip`, never Ollie or Twenty Twenty-Five. The **Update pins** workflow keeps that zip, the Blocks zip and every other pin in `.github/pins.json` on the newest release, and CI fails when one is behind; never pin a commit or an old release in a blueprint.
- Every write route checks a capability or the request signature, every input is sanitized and every output escaped. Site-editing writes keep a revision so they can be undone.
- Sites must keep working when the API can't be reached: cache answers, fail quietly in the front end, and show admins a plain notice.

## Rules for every change

- **Playground only for tests.** Never create a store, product (seller), reseller or ready-made storefront on the server to try, check or demo something. Check on WordPress Playground (the WordPress skills in `.claude/skills/`, and the plugins repo's `scripts/playground`). The API's own tests cover the server building stores. If a check truly can't run on Playground, ask the owner first, say why, and delete the store as soon as the check is done. Never keep test stores.
- **Store tests run as a site type.** Every Playground test, preview or screenshot of a customer store is one of the store template's site types (the keys of `waas-provisioning-api/templates/anypress-store/roles.json`: website, bookings, online-store, community, everything, highlevel), with AnyPress Client on and `ANYPRESS_TENANT_ROLES` set, so only that type's plugins are on, as on a real store. Never a WordPress with every plugin on and no site type. Say which site type in the report or screenshot.
- **Beads, every time.** Each piece of work gets a Beads issue in the list of the repository it changes, before it starts (check for a duplicate first). Put the id in the branch, the PR and the status, and close the issue when the PR merges or the change is live. Run `bd` in the session doing the work; the SessionStart hook in `.claude/settings.json` loads the Dolt login and sets up `.beads` from DoltHub, then `bd dolt push` syncs it. This repository's issues are in DoltHub `chowderr/waas` (new ids `waas-*`; issues moved here from another list keep their old ids). Each AnyPress repository has its own list. Work that also changes another repository gets an `also:<repo>` label (`api`, `plugins`, `dashboard`, `site`, `theme`, `blocks`, `fluentsuite`), and a task whose epic is in another list gets `epic:<id>`. Jobs that change no code (accounts, outreach, server and shop settings) go in AnyPress Ops (`chowderr/anypress_ops`, in the obsidian-vault repository under `1. Projects/WaaS/AnyPress Ops/`).
- **Pull requests:** open them ready for review, not as drafts, so CI runs. Merge a PR yourself once CI is green and the work was asked for.
- **No "WPCS" wording.** The old platform is gone. Say "the AnyPress API" or "the API's key and secret login". Don't add the word anywhere.
- **Public docs are for users.** READMEs and `docs/` explain how to use and run the code. Internal notes (server and Coolify ids, Beads, deployment steps) go in the obsidian-vault repository under `1. Projects/AnyPress/`. Never put how or why AnyPress started in public copy.
- **Official SDKs, always.** Call every outside service through its official SDK or library and configure it to fit (custom storage, base URL, options), rather than writing the HTTP calls by hand. Read the SDK's options before deciding it doesn't fit. Only where no official SDK exists, write the client yourself and say so in the PR.
- **Verify before claiming.** Check npm, wordpress.org or the official docs before calling a version or spec "the latest", and check a fix on the running system before calling it fixed.
