# Test storefront

A throwaway WordPress storefront for testing the whole chain end to end: storefront checkout → waas-host → the live provisioning API → a real store on Coolify. It's not the owner's business site, and it holds no real customer data.

## How it's built

One Coolify **Service** from [`scripts/test-storefront/compose.yml`](../scripts/test-storefront/compose.yml): `wordpress` (wordpress:6.8-php8.3-apache) and `db` (mariadb:11), with volumes `wp`, `db` and `wpcli`. The database passwords are generated by Coolify (`SERVICE_PASSWORD_*`).

Plugins:

- FluentCart 1.7, from wordpress.org. Subscriptions are built in, so nothing else is needed.
- waas-host and waas-payments, built from this repo's `packages/`.

FluentCart runs in **test** order mode. waas-host uses its FluentCart adapter, the only cart installed.

The `payments` step also sets up subscriptions and gateways:

- **Subscriptions:** FluentCart → Settings → Subscriptions is **Store managed** with **Automatic charge** on. That's what waas-payments needs to take subscriptions: FluentCart runs the schedule and charges each renewal to the card saved at checkout (see `packages/waas-payments/README.md`).
- **Gateways:** both are offered at checkout. The Card gateway runs in sandbox mode; its credentials are checked with Authorize.Net, and its Public Client Key is fetched. FluentCart's offline gateway ("Cash") doesn't charge anything, so a test subscription can be activated by hand: mark the order paid in FluentCart → Orders.
- **Feed:** the product's WaaS Provisioning feed uses waas-host's default triggers, which include `subscription_reactivated`.

[`scripts/test-storefront/storefront.py`](../scripts/test-storefront/storefront.py) does everything through the Coolify API, following the patterns in waas-provisioning-api's ADR 0001:

- **Commands** run as on-demand scheduled tasks on the service, in container `wordpress`. Tasks run as root; the `wp` wrapper drops to `www-data` (uid 33) with `setpriv`. Coolify keeps only 255 characters of a task command, so the work lives in [`remote/setup.sh`](../scripts/test-storefront/remote/setup.sh) and short PHP files.
- **Plugin code** reaches the container through a `WAAS_PKG` environment variable, 20 KB per restart. Coolify sends a service's `.env` to the server as a single shell argument, and a value of 45 KB already broke the deploy; a bind mount's `content:` of that size failed the same way. The chunks are reassembled on the `wpcli` volume (`/opt/wpcli/x`), and the variable is removed afterwards.
- **Cron:** WordPress's own cron is off (`DISABLE_WP_CRON`). A Coolify scheduled task named `wp-cron` runs `wp action-scheduler run` and `wp cron event run --due-now` every minute instead, as www-data. Without it, nothing queued runs until someone loads a page. Front-end checkouts don't start Action Scheduler's queue, so a paid order waited until the next visit before its store was created. The `cron` step sets both up.
- **Secrets** are only ever Coolify variables:
  - The admin password is generated by `create` and never printed.
  - The API key and secret come from the session's `WAAS_TEST_KEY` / `WAAS_TEST_SECRET`. `configure` copies them into WP options from the container's environment.
  - The Authorize.Net sandbox credentials come from `AUTHNET_SANDBOX_LOGIN_ID` / `AUTHNET_SANDBOX_TRANSACTION_KEY`. `payments` saves them through the gateway's own validation, so the Transaction Key is stored encrypted, as when saving the form.
  - Every variable is locked except `WP_ADMIN_PASSWORD`.
  - `WP_ADMIN_PASSWORD` is deliberately **not** locked: a locked Coolify variable (`is_shown_once`) never shows its value again, and the owner needs to read this one. Lock it after copying if you like.
  - Descriptions are plain text, because Coolify rejects JSON there.

## Rebuild, update, remove

The script needs Coolify API access: `COOLIFY_TOKEN`, or a session whose proxy injects it. It also needs `composer`, `zip` and `xz` locally.

```shell
scripts/test-storefront/storefront.py create   # project + service + variables, needs WAAS_TEST_KEY / WAAS_TEST_SECRET (and AUTHNET_SANDBOX_* for the Card gateway)
scripts/test-storefront/storefront.py push     # build the plugins and copy them in (about 2 minutes per chunk)
scripts/test-storefront/storefront.py setup    # bootstrap install plugins configure pages product payments cron
```

- **New plugin code:** run `push`, then `setup plugins check`.
- **Single steps:** `setup check` prints whether the API is reachable, the production version and the commerce adapter. Every step can be re-run safely; `install`, `pages` and `product` skip what already exists.
- **Remove everything:** `storefront.py remove` deletes the service with its volumes, then the project.
- **One-off command:** `storefront.py run '<command>'`, at most 255 characters, run as root.

## Owner steps

1. **Log in.** Copy the admin password from Coolify (see the table at the top), then log in at https://storefront-test.191.101.15.236.sslip.io/wp-admin as `admin`.
2. **Lock the password variable.** Back in Coolify, lock `WP_ADMIN_PASSWORD` (the lock icon next to it). Coolify then never shows the value again, so copy it somewhere safe first. To get back in later, use WordPress's lost-password link, or set a new password with `storefront.py run`.
3. **Check test mode.** The WordPress admin bar shows an orange **Test Mode** badge. If it says Live Mode, go to **FluentCart** → **Settings** → **Store Settings** and set the order mode to **Test**.

The Card gateway is already set up with the sandbox credentials; nothing needs entering. Sandbox test card: `4111 1111 1111 1111`, any future expiry date, any CVV.

### Changing the Authorize.Net sandbox credentials

Only needed for a different sandbox account, or if the keys are rotated.

1. **Log in to the sandbox.** Go to https://sandbox.authorize.net (not account.authorize.net). For a new account, sign up first at https://developer.authorize.net/hello_world/sandbox.html.
2. **API Login ID and Transaction Key.**
   1. Go to **Account** (top menu) → **Settings** (left) → **Security Settings** → **General Security Settings** → **API Credentials & Keys**.
   2. The **API Login ID** is shown at the top.
   3. Under **Create New Key(s)**, choose **New Transaction Key** and click **Submit**.
   4. Enter the PIN Authorize.Net emails you, then click **Verify PIN**.
   5. Copy the **Transaction Key**. It is shown only once.
3. **Public Client Key.** Open **Account** → **Settings** → **Security Settings** → **General Security Settings** → **Manage Public Client Key**. If no key is shown, click **Submit** to create one. You never paste it anywhere; the plugin fetches it.
4. **Test Mode off.** **Account** → **Settings** → **Security Settings** → **General Security Settings** → **Test Mode** should say **Live**. That is still the sandbox; in Test Mode the sandbox returns transaction ID 0.
5. **Enter the new keys.** Either:
   - in WordPress: **FluentCart** → **Settings** → **Payments** → **Authorize.Net** ("Card"). Paste both values, keep **Sandbox mode** On, keep the method on, and click **Save**. The plugin verifies them and fetches the Public Client Key; or
   - in Coolify: update `AUTHNET_LOGIN_ID` / `AUTHNET_TRANSACTION_KEY`, restart the service, then run `storefront.py setup payments`.

## Notes

- **Card subscriptions** need FluentCart's store-managed mode. Under "Gateway managed" (FluentCart's default), FluentCart doesn't offer the Card gateway for a subscription cart. The `payments` step sets store-managed mode for the whole store.
- **Plugin updates.** Don't apply plugin updates that WordPress offers for WaaS Host, WaaS Client or WaaS Payments. Update them with `push` from this repo.
